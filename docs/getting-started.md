# Getting Started & Lifecycle

## Installation

TaskEx requires **Python 3.11+** and depends only on **Pydantic**.

```bash
pip install taskex
```

## Creating a `TaskRunner`

You can instantiate `TaskRunner` either inside an `asyncio` event loop or at module import time (for example, in a web or MCP server):

```python
from taskex import Env, TaskRunner

# Safe at module level (loop setup is deferred until first async use)
runner = TaskRunner(instance_id=0, config=Env(MERCURY_SYNC_EXECUTOR_TYPE="thread"))
```

For scripts or scoped lifetimes, prefer the async context manager so cleanup tasks, running subprocesses, executors, and signal handlers are always released on exit:

```python
import asyncio
from taskex import Env, TaskRunner


async def main() -> None:
    async with TaskRunner(config=Env(MERCURY_SYNC_EXECUTOR_TYPE="none")) as runner:
        run = runner.command("echo", "hello")
        result = await runner.wait(run.token)
        print(result.result)


asyncio.run(main())
```

## Tokens

Submitting work via `runner.run(...)` or `runner.command(...)` returns a `Run` object immediately without blocking. Each `Run` exposes a string `token` formatted as:

```text
<task_name>:<run_id>
```

- `task_name` is the `alias` if provided, otherwise the callable name or command string. Task names containing colons (e.g., `"docker:build:v1"`) are supported safely because tokens are parsed from the right.
- `run_id` is a monotonically increasing 64-bit Snowflake integer generated by `TaskRunner` (unless you pass an explicit `run_id`).

Pass `run.token` to `wait()`, `wait_all()`, `get_task_update()`, `get_run_status()`, `complete()`, `cancel()`, or `cancel_schedule()`.

## Run Lifecycle & `RunStatus`

Every `Run` transitions through states defined in `RunStatus`:

| Status | Meaning | Terminal? |
| --- | --- | --- |
| `RunStatus.CREATED` | `Run` object created; execution has been scheduled on the event loop. | No |
| `RunStatus.PENDING` | Queued awaiting a semaphore slot (used by `Task._run`). | No |
| `RunStatus.IDLE` | Returned by `task.status` when a task has no runs yet. | No |
| `RunStatus.RUNNING` | Callable or subprocess is actively executing. | No |
| `RunStatus.PAUSED` | Suspended cooperatively (`pause_point`) or via POSIX `SIGSTOP` (`command`). | No |
| `RunStatus.COMPLETE` | Finished successfully (return code `0` for shell commands). | Yes |
| `RunStatus.FAILED` | Raised an exception, timed out, failed to spawn, or exited non-zero. | Yes |
| `RunStatus.CANCELLED` | Cancelled via `cancel()`, `cancel_schedule()`, `stop()`, `shutdown()`, or `abort()`. | Yes |

Both `TaskRun.complete()` and `ShellProcess.complete()` return `True` for all terminal states (`COMPLETE`, `FAILED`, `CANCELLED`). Once a run enters a terminal state, subsequent `cancel()` or `abort()` calls do not overwrite its status, and its `elapsed` duration freezes at `end - start`.

## Stopping vs Shutting Down vs Aborting

TaskEx provides three lifecycle methods on `TaskRunner`:

| Method | Sync / Async | Cancels active runs & schedules | Stops cleanup loop & executor | Runner usable afterwards? |
| --- | --- | --- | --- | --- |
| `await runner.stop()` | `async` | Yes (gracefully) | No | **Yes** |
| `await runner.shutdown()` | `async` | Yes (gracefully) | Yes | No (`RuntimeError` on new submissions) |
| `runner.abort()` | `sync` | Yes (immediately, `SIGKILL` for subprocesses) | Yes (`wait=False`) | No (`RuntimeError` on new submissions) |

- Use **`await runner.stop()`** to cancel all in-flight work and schedules while keeping the runner alive for future work.
- Use **`await runner.shutdown()`** (or `async with TaskRunner() as runner:`) for normal graceful teardown. `shutdown()` is idempotent.
- Use **`runner.abort()`** when you need an immediate, non-blocking synchronous teardown (for instance, in a synchronous cleanup callback or emergency shutdown path).
